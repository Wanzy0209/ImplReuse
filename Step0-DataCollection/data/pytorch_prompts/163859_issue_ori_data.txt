## Bug Description

When using `torch.distributed.pipelining` with `ScheduleGPipe`, gradient computations are incorrect, producing significantly different gradient values compared to single-GPU baseline. While the forward pass produces nearly identical loss [0] in the first step starting with identical model initialization and input data (confirming correct forward computation), the backward pass generates gradients that differ by orders of magnitude, making the library unusable.

It's unclear to me if the bug is in _how_ the library is being used (I thoroughly checked the documentation, api, tutorials, etc, I don't think so), or if its a bug in the backwards pass handling.

[0] not exact but within reason considering numerical issues due to floating point error / order of operation / tensor slices

## To Reproduce

1. Save the provided script as repro.py
2. Run single-GPU baseline: `python repro.py --mode single`
3. Run pipeline parallel: `torchrun --nproc_per_node=4 repro.py --mode pipeline`
4. Observe the comparison table showing _~3-4x gradient magnitude difference from step 0_

### Expected behavior

Given identical model parameters and inputs, the backward pass should produce nearly identical gradients between pipeline parallel and single-GPU execution. Minor differences due to floating-point precision are acceptable, but gradient magnitudes should be consistent. The pipeline schedule with `scale_grads=True` should properly handle gradient scaling across microbatches.
