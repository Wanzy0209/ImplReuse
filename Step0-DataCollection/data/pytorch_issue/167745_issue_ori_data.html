    Umbrella bug: failures in basic custom MemPool patterns#167745
    Copy link
    Assignees

    Description

    MatthiasKohl
    opened on Nov 13, 2025
    Issue body actions

    🐛 Describe the bug

    This is a bug to document several problematic patterns with custom MemPool allocations.
    For now, these simple tests do not include interactions with CUDA graph pools, but at the moment, custom MemPools behave very similarly to CUDA graph pools, so hopefully the current tests are sufficient for now.
    Additionally, the tests are not checking for thread-safety (for now), which will be added in the future as this was an issue previously (#152861).

    All tests can be found in this repo (which has two branches as explained per below): https://github.com/MatthiasKohl/pytorch-mempool-litmus

    Failing tests due to temporary MemPool objects:

    Test 1:

    pool1 = make_custom_pool(1)

with torch.cuda.use_mem_pool(torch.cuda.MemPool(pool1)):
    print("Pool 1 ctx start")
    x1 = torch.randn(8, device="cuda")
    print("Pool 1 ctx end")
del x1

    Test 2:

    pool1 = make_custom_pool(1)
pool2 = make_custom_pool(2)

x1 = torch.randn(8, device="cuda")
with torch.cuda.use_mem_pool(torch.cuda.MemPool(pool1)):
    print("Pool 1 ctx start")
    with torch.cuda.use_mem_pool(torch.cuda.MemPool(pool2)):
        print("Pool 2 ctx start")
        print("Pool 2 ctx end")
    print("Pool 1 ctx end")
del x1

    For these, I think an important question is: should the above pattern be allowed at all in python?
    IMO, it should: From the point of view of the user, it should not be their responsibility to keep track of when exactly the custom pool is still needed or not, especially given that the caching allocator may free tensors at a later time than the deletion of the tensor itself. Not allowing this pattern would cause unnecessary confusion IMO. In this case, the user simply wants to mark all deleted tensors as "free-able" and all non-deleted tensors as "free-able as soon as they are deleted", at the point of deleting the pool object itself.
    Note that there is currently no good way to create a temporary python object tied to the context manager other than what the above test does.

    Test 1 fails because it incorrectly uses the default cudaFree here:

    pytorch/c10/cuda/CUDACachingAllocator.cpp

    Line 3382 in c940b1f

    if (pool->owner_PrivatePool && pool->owner_PrivatePool->allocator()) {

    This is because the owner pool of the private pool isn't active anymore at the time where the blocks get released. We then call the default cudaFree which is dangerous as we have no idea whether this even works with pointers from a custom allocator.

    Test 2 fails because in the nested case, when deleting the MemPool object for pool2, we are still "capturing", thus running into the internal assert here:

    pytorch/c10/cuda/CUDACachingAllocator.cpp

    Line 3525 in c940b1f

    TORCH_INTERNAL_ASSERT(captures_underway.empty());

    All remaining simple tests in the repository fail due to the above issues related to temporary objects, so I created a side-branch of the repo to track cases where we keep references to the pools around: https://github.com/MatthiasKohl/pytorch-mempool-litmus/tree/mempool_non_temp

    In this case, we have failing tests due to incorrect nesting: many tests are essentially duplicates of #161193, e.g. the below

    Test 3:

    pool1 = torch.cuda.MemPool(make_custom_pool(1))
pool2 = torch.cuda.MemPool(make_custom_pool(2))

with torch.cuda.use_mem_pool(pool1):
    print("Pool 1 ctx start")
    with torch.cuda.use_mem_pool(pool2):
        print("Pool 2 ctx start")
        x1 = torch.randn(8, device="cuda")
        print("Pool 2 ctx end")
    print("Pool 1 ctx end")
del x1

    All remaining tests currently fail for the same reason, but depending on how the nesting issue is fixed, they may reveal further issues.
    Ideally, an incremental solution to the nesting issue should not make the situation worse (all currently passing tests should still pass).

    cc @syed-ahmed @ngimel as you're CC'ed on related issues as well

    Potential initial solutions:

    1. we need to either associate a private pool with the custom MemPool that was active at the moment of creation of the private pool, or use a completely custom deleter for tensors created through a custom MemPool. The latter would mean that MemPools would not benefit from the caching / blocking of the caching allocator at all, IIUC, but the former may cost some performance.
    2. for nesting in general, we somehow need to track the stack of active MemPools, instead of just the latest one, in captures_underway / graph_pools. This should already be possible, but I assume that the basic checks for captures_underway.empty() need to be improved s.t. we allow "captures" while releasing the blocks of the previous capture. There may be a few other spots where this needs revisiting.

    It would be great if you have further comments on the solutions :)

    Note: all tests expect the following imports/utility functions to be available:

    import os
import torch
from torch.utils import cpp_extension

CUSTOM_ALLOC_SOURCE_TEMPLATE = """
#include <cuda_runtime_api.h>
#include <iostream>
extern "C" {
void* customAlloc(size_t size, int device, void* stream) {
  std::cout << "Pool [::id::] alloc" << std::endl;
  void* ptr = nullptr;
  cudaMalloc(&ptr, size);
  return ptr;
}
void customFree(void* ptr, size_t size, int device, void* stream) {
  std::cout << "Pool [::id::] free" << std::endl;
  cudaFree(ptr);
}
}
"""

CUSTOM_ALLOCATORS = dict()


def make_custom_pool(pool_id: int) -> torch._C._CUDAPluggableAllocator:
    source = CUSTOM_ALLOC_SOURCE_TEMPLATE.replace("[::id::]", str(pool_id))
    custom_libname = f"custom_alloc{pool_id}"
    if custom_libname in CUSTOM_ALLOCATORS:
        return CUSTOM_ALLOCATORS[custom_libname][0].allocator()
    os.makedirs(f"./build_{pool_id}", exist_ok=True)
    custom_allocator = cpp_extension.load_inline(
        name=custom_libname,
        cpp_sources=source,
        with_cuda=True,
        is_python_module=False,
        build_directory=f"./build_{pool_id}",
    )
    allocator = torch.cuda.CUDAPluggableAllocator(
        f"./build_{pool_id}/{custom_libname}.so", "customAlloc", "customFree"
    )
    CUSTOM_ALLOCATORS[custom_libname] = (allocator, custom_allocator)
    return allocator.allocator()
