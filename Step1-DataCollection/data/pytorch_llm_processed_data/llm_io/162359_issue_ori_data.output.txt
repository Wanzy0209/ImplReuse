**Title**: SequentialLR aliases lr Tensor with initial_lr, corrupting base_lrs for chained schedulers

**Issue ID**: 162359

**Bug Description**: 
The issue describes a bug where:
1. When using an optimizer with a Tensor learning rate (as recommended to avoid recompilation), `SequentialLR.__init__` assigns `group["lr"] = group["initial_lr"]`, which aliases the tensors.
2. The initial step of the first scheduler writes the lr in-place, which mutates the `initial_lr` and all chained schedulers' `base_lrs` that reference it.
3. Chained schedulers which rely on `base_lrs` therefore start from the wrong base (e.g., scaled by `start_factor` if using a `LinearLR` first).

The example shows that when using a Tensor learning rate and `SequentialLR` with `schedulers=[LinearLR, CosineAnnealingLR]`, the `base_lrs` of chained schedulers (and thus `CosineAnnealingLR` outputs) are scaled by the `LinearLR`'s `start_factor`.

**Repro Code**: There's a complete reproduction script provided in the issue.

**Repro Output**: The issue mentions that the output shows the `base_lrs` of chained schedulers are scaled by the `LinearLR`'s `start_factor`, causing incorrect behavior. There are also images showing the incorrect vs correct schedule.
