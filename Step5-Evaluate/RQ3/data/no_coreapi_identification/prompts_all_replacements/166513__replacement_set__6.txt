Title: Severe Memory Leak in Dataloader on Windows when using a long-live/infinite iterator
Bug Description:
### 🐛 Describe the bug

# Description
There appears to be a significant and consistent memory leak in the PyTorch `DataLoader` on the Windows platform. The leak occurs specifically when the DataLoader's iterator is kept alive for a large number of steps (e.g., in an "infinite" sampling loop for step-based training).

The key characteristics of this bug are:
* System RAM continuously increases until the program crashes or the system becomes unresponsive.
* The leak occurs even when `num_workers=0`, indicating it is not a multiprocessing-related issue.
* The leak occurs even when pin_memory=False, indicating it is not related to CUDA pinned memory.
* With pin_memory=True: The Shared GPU Memory (as reported by Windows Task Manager) continuously increases, even if no tensors are ever moved to a CUDA device. This eventually leads to a CUDA out of memory error, while the dedicated GPU memory remains unused.
* Explicitly calling gc.collect() does not free the leaked memory, suggesting the leak is happening in a lower-level, native (C++) component, not in Python's managed memory.
* The leak is independent of the underlying I/O library, as it has been reproduced with both `OpenCV (cv2)` and `torchvision.io.read_image`.
* Crucially, a standard, finite-epoch training loop (for epoch in ...: for batch in dataloader: ...) does not leak memory.

This evidence strongly suggests that the DataLoaderIterator object accumulates native resources during its lifetime that are only released upon it
